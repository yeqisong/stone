# K道量化平台 - 特征计算模块开发设计方案（最终定稿版）


## 一、模块概述

### 1.1 模块定位

特征计算模块是 KEPL 语言体系的 **“执行层”** 。它负责将**特征管理模块**中定义的特征元数据（公式、依赖、目标实体），结合**函数管理模块**提供的原子算子，在具体的数据集上执行计算，并将结果写入对应的特征宽表。

**核心定位**：在 DAG 调度模块中，特征计算模块表现为 **“一个独立的计算节点”** 。DAG 只负责触发该节点并接收完成信号，节点内部的依赖解析、特征增加、公式变更、执行顺序优化等所有逻辑变化，**均不对外暴露**。

> **边界声明**：本模块 **只负责“如何计算”和“如何存储”**，不负责“何时计算”和“进度如何展示”。计算任务的触发由 DAG 调度模块按编排好的流程调用本模块的接口完成。本模块对外提供 **且仅提供两个稳定接口**：按日计算（`compute_daily`）和按日期段计算（`compute_range`）。

### 1.2 模块在整体架构中的位置

```
┌─────────────────────────────────────────────────────────────────┐
│                      DAG 调度模块                              │
│  负责流程编排、任务触发、并发控制、进度推送、异常重试          │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                     特征计算节点                       │   │
│  │  （DAG 视其为黑盒，仅调用 compute_daily / range）      │   │
│  └──────────────────────┬──────────────────────────────────┘   │
└─────────────────────────┼─────────────────────────────────────┘
                          │ 调用两个稳定接口
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                   特征计算模块（本模块）                        │
│  内部自包含：依赖解析、特征调度、分块计算、写入存储            │
│  特征的新增、公式修改、依赖变化，全部封闭在模块内部            │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 核心设计原则

| 原则 | 说明 |
| :--- | :--- |
| **接口稳定性** | 对外仅暴露 `compute_daily` 和 `compute_range` 两个接口，永不变化。内部所有演进不影响外部调用方。 |
| **内部自包含** | 特征的新增、依赖关系的变化、计算顺序的优化，全部在模块内部处理，DAG 无须感知。 |
| **幂等性** | 同一日期范围、同一特征可重复计算，重复执行不产生脏数据（UPSERT 语义）。 |
| **依赖感知** | 计算前自动解析特征依赖图，按拓扑顺序执行。 |
| **存储隔离** | 不同实体的特征写入不同的物理表，互不干扰。 |
| **无外部依赖** | 模块不依赖 WebSocket、消息队列等外部组件，保持纯粹的计算与存储职责。 |


## 二、物理表结构设计

> 基于 **“完整时空矩阵”** 理念，特征宽表为每个（交易日 × 实体）预置一行，通过状态列标记数据的计算状态。

### 2.1 个股特征宽表：`feature_stock`

| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| `trade_date` | DATE | PRIMARY KEY (1) | 交易日 |
| `stock_code` | VARCHAR(10) | PRIMARY KEY (2) | 股票代码 |
| `_row_status` | VARCHAR(16) | NOT NULL, DEFAULT 'ACTIVE' | 行状态：`ACTIVE` / `PRE_IPO` / `POST_DELIST` / `SUSPENDED` |
| `_calc_status` | VARCHAR(16) | NOT NULL, DEFAULT 'PENDING' | 计算状态：`COMPUTED` / `PENDING` / `NOT_APPLICABLE` |
| `_updated_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP ON UPDATE | 最后更新时间 |
| `{feature_name_1}` | DECIMAL(20,6) | NULL | 用户定义的动态特征列（如 `ma5`、`rsi`） |
| `{feature_name_2}` | DECIMAL(20,6) | NULL | 同上 |
| ... | ... | ... | 随特征注册动态扩展 |

**分区策略**：按 `trade_date` 进行**年分区**（`PARTITION BY RANGE (YEAR(trade_date))`）。

### 2.2 ETF特征宽表：`feature_etf`

结构与 `feature_stock` 一致，主键为 `(trade_date, etf_code)`。

### 2.3 指数特征宽表：`feature_index`

结构与 `feature_stock` 一致，主键为 `(trade_date, index_code)`。

### 2.4 全局特征宽表：`feature_global`

| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| `trade_date` | DATE | PRIMARY KEY | 交易日（每天仅一行） |
| `_row_status` | VARCHAR(16) | NOT NULL, DEFAULT 'ACTIVE' | 行状态 |
| `_calc_status` | VARCHAR(16) | NOT NULL, DEFAULT 'PENDING' | 计算状态 |
| `_updated_at` | DATETIME | DEFAULT CURRENT_TIMESTAMP ON UPDATE | 最后更新时间 |
| `{feature_name_1}` | DECIMAL(20,6) | NULL | 全局特征列 |
| ... | ... | ... | 随特征注册动态扩展 |

### 2.5 实体元数据表：`entity_meta`

用于维护每个实体的“有效日期范围”（上市日期、退市日期等）：

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `entity_type` | VARCHAR(16) | `stock` / `etf` / `index` |
| `entity_code` | VARCHAR(10) | 实体代码 |
| `list_date` | DATE | 上市/成立日期 |
| `delist_date` | DATE | NULL 表示至今仍在交易 |
| `is_active` | BOOLEAN | 当前是否活跃 |

### 3.2 写入策略

| 策略 | 说明 |
| :--- | :--- |
| **批量 UPSERT** | 使用 `INSERT ... ON DUPLICATE KEY UPDATE`，单次写入数千行 |
| **事务性写入** | 同一特征、同一日期的所有实体数据在一个数据库事务中完成 |
| **分批提交** | 若单次写入数据量过大（如全市场5000只股票），按每批1000行拆分提交 |


## 四、对外接口定义（模块门面）

这是本模块**对外暴露且仅暴露的两个接口**。DAG 调度模块仅需了解这两个接口的语义，模块内部的所有变化（特征新增、依赖变更、优化策略）对外完全透明。

### 4.1 接口一：按日计算

```python
def compute_daily(
    self,
    feature_name: str,              # 特征英文名
    date: str,                      # 交易日，如 '2026-06-27'
    entity_codes: Optional[List[str]] = None,  # None 表示全量实体
    force_recompute: bool = False,  # 是否强制重算已 COMPUTED 的格子
    progress_callback: Optional[ProgressCallback] = None
) -> DailyComputeReport:
    """
    计算指定特征在指定日期的值，并写入宽表。
    
    内部自动完成：
    1. 加载特征元数据（formula、depends_on、target_entity）
    2. 递归解析依赖图，生成拓扑执行顺序
    3. 按顺序计算所有依赖特征（仅算当天）
    4. 计算目标特征本身
    5. 写入宽表，更新 _calc_status = 'COMPUTED'
    
    返回：DailyComputeReport
        - feature_name: str
        - date: str
        - total_entities: int          # 应计算的实体总数
        - success_entities: int        # 成功计算的实体数
        - failed_entities: List[str]   # 失败的实体列表
        - skipped_entities: List[str]  # 已 COMPUTED 且未强制重算的实体
        - execution_time_ms: int
        - status: 'completed' | 'partial' | 'failed'
    """
    pass
```

### 4.2 接口二：按日期段计算

```python
def compute_range(
    self,
    feature_name: str,              # 特征英文名
    start_date: str,                # 起始日期
    end_date: str,                  # 结束日期
    entity_codes: Optional[List[str]] = None,  # None 表示全量实体
    force_recompute: bool = False,  # 是否强制重算
    progress_callback: Optional[ProgressCallback] = None
) -> RangeComputeReport:
    """
    计算指定特征在指定日期范围内的值，并写入宽表。
    
    内部自动完成：
    1. 加载特征元数据
    2. 递归解析依赖图，生成拓扑执行顺序
    3. 按日期分块（chunk）执行，避免内存溢出
    4. 每个 chunk 内，按拓扑顺序计算所有依赖特征
    5. 增量写入宽表，更新 _calc_status
    6. 自动处理时间序列函数的窗口边界（如 ma(5) 需要前4天数据）
    
    返回：RangeComputeReport
        - feature_name: str
        - date_range: Tuple[str, str]
        - total_days: int              # 总天数
        - total_entities: int          # 应计算的实体总数
        - total_cells: int             # 总格子数（天数 × 实体数）
        - success_cells: int           # 成功写入的格子数
        - failed_cells: int            # 失败的格子数
        - skipped_cells: int           # 已 COMPUTED 且未强制重算的格子数
        - execution_time_ms: int
        - status: 'completed' | 'partial' | 'failed'
        - error_details: Optional[Dict]  # 部分失败时的详细信息
    """
    pass
```

### 4.3 接口参数约定

| 参数 | 说明 | 校验规则 |
| :--- | :--- | :--- |
| `feature_name` | 特征英文名 | 必须在特征管理模块中已注册且 `status != 'deprecated'` |
| `date` / `start_date` / `end_date` | 交易日 | 必须在系统交易日历范围内，`start_date <= end_date` |
| `entity_codes` | 实体代码列表 | 若为 `None`，自动展开为该实体类型下的全部活跃实体；若传入列表，仅计算指定实体 |
| `force_recompute` | 强制重算 | `True` 时忽略宽表中已 `COMPUTED` 的格子，重新计算并覆盖；`False` 时跳过已 `COMPUTED` 的格子 |
| `progress_callback` | 进度回调 | 由调用方（DAG 调度层）传入，用于获取进度并自行决定如何推送 |

### 5.2 依赖解析与执行流程（内部核心逻辑）

当 `compute_daily('bias_5d', '2026-06-27')` 被调用时，内部执行流程如下：

```python
def _execute_with_dependencies(self, feature_name, date, entity_codes, force, callback):
    # 1. 加载特征元数据
    meta = feature_meta_service.get(feature_name)  # { formula, depends_on, target_entity }
    
    # 2. 递归解析依赖图
    #    例如：bias_5d → ma5 → close（原始字段）
    dep_graph = self.resolver.resolve(meta.depends_on)
    # dep_graph = {
    #   'close': {'type': 'raw', 'source': 'daily_quote'},   # 原始字段，无需计算
    #   'ma5': {'type': 'feature', 'depends_on': ['close']},
    #   'bias_5d': {'type': 'feature', 'depends_on': ['close', 'ma5']}
    # }
    
    # 3. 拓扑排序，确定执行顺序
    exec_order = self.resolver.topological_sort(dep_graph)
    # exec_order = ['close', 'ma5', 'bias_5d']
    
    # 4. 逐层执行
    context = {}  # 存储已计算的值
    for node in exec_order:
        if node == 'close':
            # 原始字段：直接从行情表读取
            context['close'] = data_adapter.get_raw_field('close', date, entity_codes)
        else:
            # 特征：获取该特征的执行器，计算
            executor = self.get_executor(node)
            # 传入当前上下文（依赖值）
            context[node] = executor.calc_single_day(date, entity_codes, context)
    
    # 5. 最终结果已在 context['bias_5d'] 中，写入宽表
    self.writer.write_features(
        entity_type=meta.target_entity,
        date=date,
        entity_codes=entity_codes,
        feature_values={'bias_5d': context['bias_5d']}
    )
```

**关键设计**：
- **原始字段（如 `close`）**：直接从行情数据表读取，不触发任何特征计算。
- **特征依赖**：递归解析，确保依赖先于被依赖执行。
- **上下文传递**：已计算的特征值存入 `context` 字典，供后续特征引用，避免重复计算。
- **循环依赖检测**：若拓扑排序失败（存在环），抛出 `CircularDependencyError`，终止执行。

### 5.3 按日计算 vs 按段计算的区别

| 维度 | `compute_daily` | `compute_range` |
| :--- | :--- | :--- |
| **依赖特征计算范围** | 依赖特征**仅计算当天** | 依赖特征**在整个日期段内**计算 |
| **时间序列窗口** | 自动向前拉取历史原始数据（如 `ma(5)` 需前4天 `close`） | 自动向前拉取历史原始数据，且跨 chunk 边界保留上下文 |
| **内存管理** | 单日数据量小，一次性加载 | 按 `chunk_days` 分块（默认30天），逐块计算并释放 |
| **适用场景** | 每日收盘后的增量更新、单日补数 | 新特征的历史回填、全量重算 |
| **性能优化** | 无额外优化 | 跨特征共享计算结果（多个特征依赖同一个 `ma5` 时只算一次） |


## 六、进度暴露机制

### 6.1 设计原则

特征计算模块**不主动推送进度**，而是通过 **`ProgressCallback` 回调接口** 向外暴露进度信息。由调用方（DAG 调度模块）决定如何将进度转换为 WebSocket 消息、日志或数据库记录。

### 6.2 回调接口定义

```python
class ProgressCallback:
    def on_start(self, total_steps: int, total_entities: int, total_days: int):
        """任务启动时调用"""
        pass
    
    def on_dependency_resolved(self, exec_order: List[str]):
        """依赖解析完成时调用，展示执行顺序"""
        pass
    
    def on_feature_start(self, feature_name: str, step: int, total_steps: int):
        """单个特征开始计算时调用"""
        pass
    
    def on_feature_progress(self, feature_name: str, processed: int, total: int, percent: float):
        """单个特征计算过程中调用（按实体分块时）"""
        pass
    
    def on_feature_complete(self, feature_name: str, rows_written: int, elapsed_ms: int):
        """单个特征计算完成时调用"""
        pass
    
    def on_chunk_complete(self, chunk_index: int, total_chunks: int, elapsed_ms: int):
        """按段计算时，每个 chunk 完成时调用"""
        pass
    
    def on_task_complete(self, result: ComputeReport):
        """全部任务完成时调用"""
        pass
    
    def on_task_failed(self, error: Exception):
        """任务失败时调用"""
        pass
    
    def is_cancelled(self) -> bool:
        """返回 True 表示任务已被取消，模块应优雅终止"""
        return False
```

### 6.3 调用方使用示例（DAG 调度模块）

```python
# DAG 调度模块在调用特征计算时，传入实现了 ProgressCallback 的实例
class DAGProgressCallback(ProgressCallback):
    def __init__(self, task_id: str, dag_context):
        self.task_id = task_id
        self.dag_context = dag_context
    
    def on_feature_progress(self, feature_name: str, processed: int, total: int, percent: float):
        # DAG 调度层决定如何将进度推送给前端
        self.dag_context.send_ws_message({
            "topic": "dag.task.progress",
            "task_id": self.task_id,
            "event": "feature_progress",
            "data": {
                "feature_name": feature_name,
                "processed": processed,
                "total": total,
                "percent": percent
            }
        })

# 调用特征计算
result = feature_engine.compute_range(
    feature_name='bias_5d',
    start_date='2026-01-01',
    end_date='2026-06-27',

```


## 七、错误处理与容错

| 异常类型 | 处理策略 | 返回状态 |
| :--- | :--- | :--- |
| **依赖特征不存在** | 抛出 `DependencyNotFoundError`，终止计算 | `status='failed'` |
| **循环依赖** | 抛出 `CircularDependencyError`，终止计算 | `status='failed'` |
| **特征未注册或已弃用** | 抛出 `FeatureNotFoundError`，终止计算 | `status='failed'` |
| **日期不在交易日历中** | 跳过该日期，继续计算其他日期 | `status='partial'`，记录跳过日期 |
| **单个实体计算失败** | 记录失败实体，继续计算其他实体 | `status='partial'`，`failed_entities` 列表记录 |
| **数据库写入超时** | 重试 3 次，仍失败则回滚当前批次 | `status='partial'` |
| **内存溢出** | 自动降低 `chunk_days`，重新执行 | 内部自动恢复，不对外暴露 |
| **用户取消任务** | 检测 `callback.is_cancelled()`，优雅终止 | `status='cancelled'` |

## 十一、总结

本模块的核心设计理念是 **“对外极简，对内完备”** ：

- **对外**：仅暴露 `compute_daily` 和 `compute_range` 两个接口，参数稳定，语义清晰。DAG 调度模块只需调用这两个接口，传入特征名、日期范围和回调函数即可。
- **对内**：依赖解析、特征调度、分块策略、内存管理全部封闭在模块内部。特征的新增、公式的修改、依赖关系的变化，全部由本模块自行适应，**DAG 调度模块无需感知，无需修改**。

这确保了 DAG 调度模块的可编排性不受特征数量的膨胀和依赖关系的变化所影响，实现了 **“流程编排与特征逻辑的彻底解耦”** 。
