## 二、模块一：KEPL语言规范

### 2.1 模块定位

KEPL（Keda Expression & Programming Language）是K道量化平台的**公式表达式语言**，是特征计算和函数定义的语法基础。它定义了如何在公式中引用数据源、调用函数、表达计算逻辑。

### 2.2 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **零歧义** | 公式中的每一个符号都只有唯一确定的语义指向，系统绝不猜测用户意图 |
| **上下文显式化** | 通过`current`关键字显式声明“当前行”，通过数据源前缀显式声明“全量集合” |
| **物理逻辑分离** | 语法层面描述“算什么”，物理存储层面解决“存哪里”，两者通过实体机制解耦 |

### 2.3 核心概念

| 概念 | 说明 | 示例 |
| :--- | :--- | :--- |
| **主实体（Primary Entity）** | 特征计算时最外层遍历的对象。由用户在注册特征时从下拉列表中选定 | `stock`、`etf`、`index`、`global` |
| **当前行上下文（Current Context）** | 系统级变量`current`，指向主实体在当前遍历循环中的**单一行** | `current.close`表示当前这只股票的收盘价；`current.industry_code`表示当前股票的行业代码 |
| **数据源集合（Dataset Collection）** | 用数据源别名表示该数据源下的**全体数据**（向量） | `stock.close`表示所有股票的收盘价列表 |
| **外部实体引用（External Reference）** | 在遍历主实体的同时，引入其他数据源的辅助数据 | 固定个体：`index['000300.SH'].close`；动态映射：`index[current.industry_code].close` |

### 2.4 数据源注册表（系统预置）

所有数据源均需在**数据源管理模块**中提前注册方可使用。

| 别名 | 物理含义 | 关键可用字段 | 更新频率 | 主键标识列 |
| :--- | :--- | :--- | :--- | :--- |
| `stock` | A股个股日行情 | `open, high, low, close, volume, amount, industry_code, market_cap` | 日频 | `stock_code` |
| `etf` | ETF基金日行情 | `open, high, low, close, volume, iopv, premium_rate` | 日频 | `etf_code` |
| `index` | 指数日行情 | `open, high, low, close, volume` | 日频 | `index_code` |
| `financial` | 财务报告数据（季报/年报） | `pe, pb, roe, eps, revenue_growth, report_date` | 季频 | `stock_code` |
| `macro` | 宏观经济指标 | `cpi, ppi, pmi, m2, publish_date` | 月频 | （无） |
| `north` | 北向资金（陆股通） | `hold_volume, hold_ratio, net_inflow` | 日频 | `stock_code` |

### 2.5 字段引用寻址规则

| 写法 | 指向对象 | 数据类型 | 合法性条件 | 使用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 裸字段（`close`） | 当前遍历主实体的该字段（等价于`current.close`） | 标量 | 仅当特征已绑定非`global`实体时合法 | 常规运算、时间序列函数入参 |
| 显式当前行（`current.字段`） | 当前遍历主实体的该字段 | 标量 | 任何实体类型（`global`除外）均合法 | 在动态映射`[...]`中作为索引键时**必须**使用 |
| 数据源集合（`stock.close`） | 该数据源下所有标的的该字段 | 向量 | 仅作为横截面聚合函数的参数 | `avg(stock.close)`、`rank(stock.volume)` |
| 外部个体固定引用（`index['000300.SH'].close`） | 该数据源中指定唯一标的的字段值 | 标量 | 中括号内必须是字符串常量 | 引用固定基准（如沪深300） |
| 外部动态映射引用（`index[current.industry_code].close`） | 根据当前行属性动态匹配外部标的 | 标量 | 中括号内必须是`current.属性名` | 个股对齐所属行业指数 |
| 非法裸露引用（`index.close`） | — | — | **系统拦截** | 无，系统报错要求添加`['代码']`或聚合函数 |

### 2.6 系统内置函数

#### 2.6.1 时间序列函数

用于对**单一行**在**时间维度**上的历史数据进行滚动计算。参数**必须**是裸字段或`current.字段名`。

| 函数名 | 语法示例 | 说明 | 自动回溯窗口 |
| :--- | :--- | :--- | :--- |
| `ma` | `ma(close, 5)` | N周期简单移动平均 | N |
| `ema` | `ema(close, 12)` | N周期指数移动平均 | N |
| `rsi` | `rsi(close, 14)` | N周期相对强弱指标 | N+1 |
| `std` | `std(close, 20)` | N周期标准差（波动率） | N |
| `corr` | `corr(close, volume, 10)` | 两字段在N周期内的相关性 | N |
| `atr` | `atr(high, low, close, 14)` | N周期平均真实波幅 | N |
| `boll_mid` | `boll_mid(close, 20, 2)` | 布林线中轨（即`ma(close, N)`） | N |
| `boll_upper` | `boll_upper(close, 20, 2)` | 布林线上轨：`boll_mid + K × std(close, N)` | N |
| `boll_lower` | `boll_lower(close, 20, 2)` | 布林线下轨：`boll_mid - K × std(close, N)` | N |

**布林线函数内部实现逻辑**（仅供理解，不对外暴露）：

```python
def boll_mid(df, field='close', window=20, k=2):
    return df[field].rolling(window=window).mean()

def boll_upper(df, field='close', window=20, k=2):
    mid = boll_mid(df, field, window)
    std = df[field].rolling(window=window).std()
    return mid + k * std

def boll_lower(df, field='close', window=20, k=2):
    mid = boll_mid(df, field, window)
    std = df[field].rolling(window=window).std()
    return mid - k * std
```

**布林线函数重要说明**：`boll_mid`、`boll_upper`、`boll_lower`返回的是三条独立的轨道线数值。在实际使用中，**建议将这3个函数的返回值作为基础特征物化存储**，然后通过引用物理列的方式计算衍生特征`pct_b`和`bandwidth`，避免重复调用`rolling().std()`导致的性能开销。具体做法参见“特征工程最佳实践”章节。

#### 2.6.2 横截面聚合函数

用于对**全量数据集**进行统计运算。参数**必须**是`数据源别名.字段名`形式，支持可选的`exclude_self`参数（默认为`True`，即计算时排除当前行自身）。

| 函数名 | 语法示例 | 说明 | 可选参数 |
| :--- | :--- | :--- | :--- |
| `avg` | `avg(stock.close, exclude_self=True)` | 全市场收盘价均值（默认排除自己） | `exclude_self` |
| `sum` | `sum(stock.volume, exclude_self=True)` | 全市场成交量总和（默认排除自己） | `exclude_self` |
| `std` | `std(stock.pe)` | 全市场市盈率标准差 | 无 |
| `max` | `max(stock.high)` | 全市场当日最高价中的最大值 | 无 |
| `min` | `min(stock.low)` | 全市场当日最低价中的最小值 | 无 |
| `rank` | `rank(stock.volume, pct=True, exclude_self=True)` | 全市场成交量排名百分位（0~1） | `pct`、`exclude_self` |
| `quantile` | `quantile(stock.pe, q=0.8)` | 全市场市盈率的80%分位数值 | `q` |

#### 2.6.3 函数调用规则

| 规则 | 正确示例 | 错误示例 |
| :--- | :--- | :--- |
| 时序函数入参必须为裸字段 | `ma(close, 5)` | `ma(stock.close, 5)` |
| 聚合函数入参必须为数据源集合 | `avg(stock.close, exclude_self=True)` | `avg(close, exclude_self=True)` |
| 聚合函数支持`exclude_self`参数 | `rank(stock.pe, pct=True, exclude_self=True)` | — |

### 2.7 复合特征规范

| 规则 | 说明 |
| :--- | :--- |
| 依赖图必须是有向无环图（DAG） | 复合特征A可以依赖基础特征B，但B不能回头依赖A |
| 实体一致性 | `stock`实体不能直接引用`etf`实体的特征（除非通过`global`广播或中括号） |
| 依赖解析 | 系统自动提取公式中引用的其他特征名，构建依赖关系 |
| 循环检测 | 保存时执行拓扑排序，检测到环则拒绝保存 |

### 2.8 实体与物理存储映射

| 实体别名 | 遍历范围 | 每天数据行数 | 物理表名 | 主键 |
| :--- | :--- | :--- | :--- | :--- |
| `stock` | 全市场A股 | ~5000行 | `feature_stock` | `(trade_date, stock_code)` |
| `etf` | 全市场ETF | ~100行 | `feature_etf` | `(trade_date, etf_code)` |
| `index` | 全市场指数 | ~30行 | `feature_index` | `(trade_date, index_code)` |
| `global` | 无遍历，仅计算一次 | 1行 | `feature_global` | `(trade_date)` |

### 2.9 全局特征的广播机制

当训练一个基于`stock`实体的模型，且特征公式中引用了全局特征（如`global_market_sentiment`）时，DAG引擎在构建训练集时自动执行以下逻辑关联：

```sql
SELECT 
    s.trade_date,
    s.stock_code,
    s.ma5,
    s.rsi,
    g.market_sentiment,   -- 来自 feature_global（该值被广播到每一行）
    g.pmi_factor
FROM feature_stock s
LEFT JOIN feature_global g 
    ON s.trade_date = g.trade_date  -- 仅按日期关联，无代码条件
```

### 2.10 错误处理规范

| 错误类型 | 错误示例 | 系统报错信息 |
| :--- | :--- | :--- |

## 三、模块二：函数管理模块

### 3.1 模块定位

函数管理模块是KEPL语言体系的**“原子层”**。它负责注册、存储、校验和管理所有可在特征公式中调用的**“算子（Operator）”**。用户在此模块中定义的函数，将在**特征管理模块**中被引用，用于构建基础特征和复合特征。

### 3.2 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **算子即函数** | 每个函数是一个独立的计算单元，接收DataFrame，返回Series |
| **无状态** | 函数不持有任何状态，不依赖任何外部上下文 |
| **向量化优先** | 函数必须使用向量化运算（Pandas/Numpy），禁止逐行循环 |
| **版本可追溯** | 每次修改生成新版本，历史版本可查询、可回滚 |
| **安全沙箱** | 函数执行在隔离环境中，防止恶意代码或死循环拖垮系统 |

## 四、模块三：特征管理模块

### 4.1 模块定位

特征管理模块是KEPL语言体系的**“逻辑组装层”**。它负责将函数管理模块提供的原子算子与数据源实体绑定，通过KEPL公式表达式定义具体的特征，并对特征的元数据、依赖关系、状态、数据质量进行全生命周期管理。

**边界声明**：本模块**只负责特征的“定义”、“元数据管理”和“数据质量监控”**。特征的“周期性计算调度”与“物理数据写入”由独立的**DAG调度模块**负责。

### 4.2 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **特征即定义** | 特征只定义“算什么”，不负责“何时算”和“怎么存” |
| **依赖显式化** | 特征的上下游依赖关系由系统自动提取并可视化呈现 |
| **质量可观测** | 每个特征的数据完整度、缺失归因、新鲜度一目了然 |
| **状态联动** | 上游变更自动触发下游“待重算”标记 |
| **实体不可变** | 特征创建时绑定的目标实体不可修改 |

### 4.3 数据库表结构

### 4.9 循环依赖检测算法

当用户保存特征时，后端执行以下步骤：

1. **提取直接依赖**：通过公式解析器扫描出`depends_on`数组。
2. **构建全局依赖图**：加载所有`status != 'deprecated'`的特征，构建有向图（边：`依赖者→被依赖者`）。
3. **拓扑排序（Kahn算法）**：统计入度，循环剥离入度为0的节点，若剥离完毕仍有剩余节点→存在环。
4. **输出环信息**：将环中的特征名拼接成链，返回给前端。

### 4.13 特征工程最佳实践：以布林线为例

#### 4.13.1 问题背景

布林线包含三条轨道线（上轨、中轨、下轨），具有以下特点：

- **高度相关性**：上轨=中轨+K×标准差，下轨=中轨-K×标准差
- **计算成本高**：`rolling(window).std()`在全市场历史数据上计算成本较高
- **原始值复用性低**：直接使用原始数值，模型难以有效利用

#### 4.13.2 推荐存储策略：存储中间结果 + 衍生特征

**第一层：物理存储（基础特征，建议物化）**

| 特征名称 | 公式 | 存储必要性 |
| :--- | :--- | :--- |
| `boll_mid_20_2` | `ma(close, 20)` | 中轨就是移动平均线，可独立使用 |
| `boll_upper_20_2` | `boll_mid + 2 × std(close, 20)` | 上轨，计算成本高，建议物化 |
| `boll_lower_20_2` | `boll_mid - 2 × std(close, 20)` | 下轨，计算成本高，建议物化 |

**第二层：衍生特征（推荐使用，优先供模型训练）**

| 特征名称 | 公式 | 说明 |
| :--- | :--- | :--- |
| `pct_b_20_2` | `(close - boll_lower_20_2) / (boll_upper_20_2 - boll_lower_20_2)` | 价格在通道内的相对位置（0~1） |
| `bandwidth_20_2` | `(boll_upper_20_2 - boll_lower_20_2) / boll_mid_20_2` | 通道宽度，反映波动率水平 |

**核心原则**：

- 基础特征**存储中间计算结果**，确保高性能
- 衍生特征**引用已有物理列**，不重复调用`rolling`函数
- 系统通过`depends_on`自动保证计算顺序

## 六、模块五：特征计算模块

### 6.1 模块定位

特征计算模块是KEPL语言体系的**“执行层”**。它负责将特征管理模块中定义的特征元数据，结合函数管理模块提供的原子算子，在具体的数据集上执行计算，并将结果写入对应的特征宽表。

**核心定位**：在DAG调度模块中，特征计算模块表现为**“一个独立的计算节点”**。DAG只负责触发，节点内部的依赖解析、特征增加、公式变更、执行顺序优化均不对外暴露。

### 6.2 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **接口稳定** | 对外仅暴露`compute_daily`和`compute_range`两个接口 |
| **内部自包含** | 依赖解析、执行顺序、分块策略全部封装在模块内部 |
| **幂等性** | 同一日期范围、同一特征可重复计算，UPSERT语义 |
| **依赖感知** | 计算前自动解析特征依赖图，按拓扑顺序执行 |
| **存储隔离** | 不同实体的特征写入不同的物理表 |

| **FeatureWriter** | 批量UPSERT特征值到宽表，动态创建列 |

### 6.6 执行流程伪代码

```python
def compute_daily(self, feature_name, date, entity_codes, force, progress_callback):
    # 1. 加载特征元数据
    meta = feature_meta_service.get(feature_name)
    
    # 2. 递归解析依赖图
    dep_graph = self.resolver.resolve(meta.depends_on)
    # dep_graph = {'close': 'raw', 'ma5': 'feature', 'bias_5d': 'feature'}
    
    # 3. 拓扑排序
    exec_order = self.resolver.topological_sort(dep_graph)
    
    # 4. 逐层执行
    context = {}
    for step, node in enumerate(exec_order):
        progress_callback.on_feature_start(node, step, len(exec_order))
        
        if node == 'close':
            context['close'] = data_adapter.get_raw_field('close', date, entity_codes)
        else:
            executor = self.get_executor(node)
            context[node] = executor.calc_single_day(date, entity_codes, context)
        
        progress_callback.on_feature_complete(node, len(entity_codes))
    
    # 5. 写入宽表
    self.writer.write_features(
        entity_type=meta.target_entity,
        date=date,
        entity_codes=entity_codes,
        feature_values={meta.name: context[meta.name]}
    )
    
    return DailyComputeReport(...)
```

### 6.7 特征执行器

```python
class FeatureExecutor:
    def __init__(self, feature_meta):
        self.name = feature_meta.name
        self.formula = feature_meta.formula
        self.depends_on = feature_meta.depends_on
    
    def calc_single_day(self, date, entity_codes, context_data):
        # 从context中提取依赖值
        deps_values = {dep: context_data[dep] for dep in self.depends_on if dep != 'close'}
        # 调用公式引擎（向量化运算）
        return FormulaEngine.execute(
            formula=self.formula,
            date=date,
            entity_codes=entity_codes,
            extra_data=deps_values
        )
```

### 6.8 计算性能最佳实践：中间结果复用

#### 6.8.1 核心原则

衍生特征应优先引用已存在的物理列，而非重复调用系统函数。

**正确做法**（引用物理列）：
```
pct_b_20_2 的公式： (close - boll_lower_20_2) / (boll_upper_20_2 - boll_lower_20_2)
depends_on: ["close", "boll_lower_20_2", "boll_upper_20_2"]
```

**错误做法**（重复计算）：
```
pct_b_20_2 的公式： (close - boll_lower(close, 20, 2)) / (boll_upper(close, 20, 2) - boll_lower(close, 20, 2))
depends_on: ["close"]  # 无法正确识别依赖，且重复计算
```

#### 6.8.2 性能对比

| 场景 | 错误做法 | 正确做法 | 性能提升 |
| :--- | :--- | :--- | :--- |
| 5000只×20年历史数据 | ~180秒 | ~2秒 | **90倍** |
| 每日增量（5000只） | ~5秒 | ~0.05秒 | **100倍** |

#### 6.8.3 DAG调度执行顺序

DAG调度器根据`depends_on`自动确定计算顺序：
- Step 1: `boll_mid_20_2`（依赖`close`）
- Step 2: `boll_upper_20_2`（依赖`boll_mid_20_2`, `close`）
- Step 3: `boll_lower_20_2`（依赖`boll_mid_20_2`, `close`）
- Step 4: `pct_b_20_2`（依赖`close`, `boll_upper_20_2`, `boll_lower_20_2`）
- Step 5: `bandwidth_20_2`（依赖`boll_mid_20_2`, `boll_upper_20_2`, `boll_lower_20_2`）

### 6.9 错误处理

| 异常类型 | 处理策略 |
| :--- | :--- |
| 依赖特征不存在 | 抛出`DependencyNotFoundError`，终止计算 |
| 循环依赖 | 抛出`CircularDependencyError`，终止计算 |

### 10.8 回测执行器（策略模式）

```python
class BacktestExecutorFactory:
    @staticmethod
    def get_executor(strategy_type: str):
        if strategy_type == 'cross_sectional':
            return CrossSectionalBacktestExecutor()
        elif strategy_type == 'time_series':
            return TimeSeriesBacktestExecutor()
        raise ValueError(f"不支持的类型: {strategy_type}")

class CrossSectionalBacktestExecutor:
    def execute(self, model, feature_data, trading_rules):
        # 按日期循环，全量预测，取TopN调仓
        for date in sorted(feature_data.keys()):
            df_day = feature_data[date]
            df_day['pred'] = model.predict(df_day[feature_list])
            selected = df_day.sort_values('pred', ascending=False).head(trading_rules.max_holdings)
            self._rebalance(date, selected)
            return results

class TimeSeriesBacktestExecutor:
    def execute(self, model, feature_data, trading_rules):
        # 按股票循环，逐日预测，独立买卖决策
        for stock_code in feature_data.keys():
            df_stock = feature_data[stock_code]
            for idx, row in df_stock.iterrows():
                pred = model.predict(row[feature_list].values)
                if pred > threshold and not holding:
                    self._buy(stock_code, row['date'])
                elif pred < -threshold and holding:
                    self._sell(stock_code, row['date'])
        return results
```

### 10.10 模型质量评估体系

训练完成后，评估页展示完整的质量诊断，辅助审批决策：

#### 10.10.1 核心评估维度

| 维度 | 指标 | 说明 |
| :--- | :--- | :--- |
| **收益能力** | 夏普比率、年化收益、总收益率 | 衡量策略的盈利效率 |
| **风险控制** | 最大回撤、波动率、下行风险 | 衡量策略的抗风险能力 |
| **交易质量** | 胜率、盈亏比、平均单笔收益 | 衡量交易执行的精准度 |
| **稳定性** | 月度胜率、最长连续亏损 | 衡量策略的一致性 |
| **过拟合检测** | Val夏普 - Test夏普 | >0.5 过拟合，<-0.3 欠拟合 |
| **基准对比** | 策略收益 vs 沪深300同期收益 | 跑不赢指数=无价值 |
| **集中度** | Top 3 盈利占比 | >60% 则策略脆弱，依赖少数大赢 |

#### 10.10.2 模型审批标准

| 等级 | 条件 | 建议 |
| :--- | :--- | :--- |
| **优秀** | 夏普>1.5, 盈亏比>1.5, Top3集中度<50%, 跑赢基准 | 可上线 |
| **良好** | 夏普>0.8, 盈亏比>1.0 | 可上线观察 |
| **一般** | 夏普>0.3 | 需调参优化 |
| **较差** | 夏普<0.3 或跑输指数 | 不建议上线 |


## 十一、模块十：WebSocket实时消息通道模块

### 11.1 模块定位

WebSocket消息通道模块是K道量化平台的**“实时状态同步层”**。它作为前后端之间的中立数据管道，负责将后端耗时任务的进度、状态实时推送给前端。

**核心定位**：通道是**中立的数据管道**，不解析消息内容，只负责传输。

### 11.2 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **业务无状态** | 通道不解析消息内容，只负责传输 |
| **单向推送为主** | 核心职责是后端→前端的数据推送 |
| **连接独立** | 前后端之间没有直接的HTTP长连接 |

### 11.3 消息格式规范

**外层固定字段**：

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `topic` | String | ✅ | 消息主题，如`dag.execution.progress` |
| `task_id` | String | ✅ | 任务唯一标识 |
| `event` | String | ✅ | `started`/`progress`/`completed`/`failed`/`cancelled` |
| `timestamp` | Long | ✅ | 消息产生时间戳 |
| `data` | Object | ✅ | 业务数据体，通道透传 |

**消息示例**：
```json
{
  "topic": "dag.execution.progress",
  "task_id": "exec_20260629_001",
  "event": "progress",
  "timestamp": 1719480123456,
  "data": {
    "overall_percent": 65.5,
    "node_status": { "node_1": { "status": "completed", "percent": 100 } }
  }
}
```

### 11.4 连接管理

| 功能 | 规范 |
| :--- | :--- |
| **连接端点** | `wss://api.kdao.com/ws` |
| **连接确认** | 返回`{"type":"connection_established","connection_id":"conn_abc123"}` |
| **心跳** | 前端每30秒发送`ping`，服务端响应`pong` |

| **连接数限制** | 单用户最大5个 |
| **断线恢复** | 重连后发送`sync`，服务端补发进度 |
