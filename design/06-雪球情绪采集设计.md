# 06 - 雪球情绪采集设计（常驻轮询 · 帖子级增量 · 散户情绪特征）

> 版本：v1.2（2026-09-24，P3 前置：治理视图 + LLM 情绪打分试点回填）
> 目标：每日全市场（~5400 只）拉取雪球个股讨论帖的**当日增量**，形成日内时间序列情绪数据，为 P3 的情绪特征（评论脉冲 / 看涨比）与 Alpha 建模供数。
> 姿态：**常驻轮询进程 + 全局预算调度**，不是每晚集中抓取，也不是高并发轰炸。
>
> **状态**：设计已与用户逐点确认（§2）；P0 标定完成（§9.1-9.8）；P1 试点、P2 全市场 + 状态页指示灯已上线运行（§9.9）；P3 前置的公告/水军治理与 LLM 情绪打分试点已完成（§9.10，含 prompt A/B 与吞吐实测）。

## 1. 可行性结论与请求数学（为什么不是"并发 5000"）

- 雪球核心接口（个股讨论列表族）强制 `xq_a_token` cookie；频控按 token 与 IP 双维度，阈值不公开、**必须实测标定**（P0）。
- 总量约束：单 token 约 2~3 req/s，token 池 3~4 个约 6~10 req/s 预算。
- **并发 5000 被否决**：全市场一轮仅需 ~1.1 万请求，5000 在途请求是攻击级速率，秒级封禁且法律上站不住，对目标零增益。
- **每股独立循环被否决**：5400 个各自随机 sleep 的循环，全局速率只"平均合规"，单股翻页/重试叠加时瞬时击穿不可控。改为**集中调度：全局令牌桶 + 到期堆**，瞬时速率恒在预算内。
- 分档轮询的稳态速率（盘中）：

| 档位 | 初始规模 | 盘中周期 | 初始分层依据 |
|---|---|---|---|
| T1 热 | ~500 只 | 15 分钟 | 成交额 top + 雪球关注数 |
| T2 中 | ~1500 只 | 60 分钟 | 同上 |
| T3 冷 | ~3400 只 | 4 小时 | 长尾自动落此档 |

稳态合计 ~1.2 req/s，红线 3~5 req/s 留足翻页与重试余量。
> ⚠️ **P0 实测修正**：上述速率档在**匿名 token 下不可行**（行为评分制，§9.3）——匿名侧稳态上限实测 0.15 req/s 可长跑、更高需脉冲+洗白；登录 token 配额未实测。分档结构不变，速率预算改为按 token 类型动态计算（§9.4）。
- 存储：5~6 万帖/天，清洗后单行 ~1KB → **20~30GB/年**，`xueqiu_status` 按年分区（对齐 feature_values 惯例）。

## 3. 总体架构

```
配置（.env: XUEQIU_TOKENS；strategy_config: 速率/档位参数）
        │
        ▼
【xueqiu_poller · 独立常驻进程】
 │
 │  时段引擎   ←─ trade_calendar（交易日/时段判定，驱动速率曲线）
 │  分档引擎   ←─ stock_master（全市场清单）+ 每日成交额
 │  到期堆     （每股一个 next_due_at，带随机抖动）
 │  令牌桶     （全局 QPS 红线 3~5 req/s，瞬时也合规）
 │  XueqiuGuard（token 池轮换 / 指数退避 / 熔断 / 健康缓存）
 │  写缓冲     （满 200 条或 60s 攒批 UPSERT）
 │
 ├──HTTPS──→ 雪球个股讨论接口（xq_a_token cookie）
 │
 └──写入──→ PostgreSQL
             ├─ xueqiu_status      （帖子，status_id 主键，按年分区）
             └─ xueqiu_crawl_state （游标 / 档位 / next_due_at / 健康态）
                        │
                        ▼
             FastAPI 状态页卡片 + WS 进度（复用现有通道）
                        │
                        ▼  （P3，后续）
             KEPL 情绪特征：xq_comment_cnt_1d / xq_bull_ratio / 盘中脉冲
```

与现有系统的关系：
- **不触碰主链路**：行情 DAG / tushare / baostock / feature_compute 全部不动；雪球侧任何故障最多损失当天情绪数据。
- **复用**：trade_calendar（时段判定）、stock_master（股票清单）、risk_alerts 表与 WS/Chrome 通知通道（熔断告警）、状态页配额卡片模式（监控卡片）、writers 的 UPSERT 幂等模式。
- **不进 TaskManager**（其并发 ≤5 是任务级语义，不适配常驻进程）；不注册 DAG 节点。

## 4. 核心设计

### 4.1 主循环（已确认稿）

```
【启动】
  ├─ 加载配置 → token 池初始化 + 健康探测
  ├─ 从 xueqiu_crawl_state 恢复游标 / 档位 / 到期堆
  └─ 首次运行（冷启动）：全市场扫一遍列表第一页，只建立游标基线

【主循环】每 tick：
  ① 时段判定（trade_calendar + 本地时钟）
  │     交易日 09:15–15:30 → 100% 速率
  │     交易日 15:30–23:00 → 50%（盘后讨论活跃）
  │     交易日 23:00–08:30 → 停（主调度休眠）
  │     非交易日全天       → 20%
  ▼
  ② 从到期堆取 next_due_at ≤ now 的股票（随机抖动打散顺序）
  ▼
  ③ 令牌桶有余量？──否──→ 等待下个 tick（绝不击穿红线）
  │ 是
  ▼
  ④ 拉该股讨论列表第一页（count=20，池中 token 轮换）
  │
  ├─ 成功：
  │    ├─ 对比游标算新增；新增 > 20 → 翻页直至游标（单轮上限 5 页保护）
  │    ├─ 新增帖子 → 写缓冲（攒批落 xueqiu_status）
  │    ├─ 更新游标；next_due_at = now + 档位周期 × 0.8~1.2 随机抖动
  │    └─ 自适应调档：连续 3 轮零新增 → 降一档
  │                    连续 2 轮新增 ≥ 1 页 → 升一档
  │
  └─ 失败：
       ├─ 网络超时 → 指数退避，next_due_at 后移，不阻塞其他股票
       ├─ 429 / 风控错误码 → 退避 + 换 token 重试
       ├─ 单 token 连续失败 ≥5 → 标记不健康，移出池
       └─ token 池耗尽 → 全局熔断：暂停调度 + risk_alerts 告警
                          + 定时探测恢复或人工补 token

【兜底轮】每晚 23:30：只重访当日失败/被退避股票，出日终统计
【恢复】进程重启：直接从 crawl_state 续跑，无人工介入
```

### 4.2 调度器（集中式，D2）

- **到期堆**：小顶堆按 `next_due_at` 排序，tick 时弹出到期者；`next_due_at = now + 档位周期 × U(0.8, 1.2)`，随机抖动既打散请求指纹又避免整档同步到期。
- **令牌桶**：全局单桶，速率 = 红线 × 时段系数。所有请求（轮询/翻页/重试/token 健康探测）从同一桶取令牌，互相挤兑但永不击穿。
- **时段引擎**：读 trade_calendar 判交易日，本地时钟判时段，输出速率系数（100% / 50% / 20% / 停）。

### 4.3 分档与自适应（D3）

- 初始分层：成交额 top（T1），关注数与成交额混合（T2），其余 T3；P0 前 tushare 无雪球关注数，首版可用成交额单独分层，关注数字段若接口可得再引入。
- 自适应（阈值 P1 实测后调整）：`zero_streak ≥ 3` 降一档；`full_streak ≥ 2`（连续整页新增）升一档。档位持久化在 crawl_state，重启不丢。
- 兜底约束：T3 周期下限 = 4h（交易日内至少覆盖一轮），防止全部沉底。

### 4.4 XueqiuGuard（token 池 / 频控 / 熔断）

对标 TushareQuota 的角色定位，但逻辑不同（滑窗限速而非次/天计数）：
> ⚠️ **P0 实测修正（§9.3）**：频控不是"次数配额"而是**阿里云 WAF 行为评分制**——匿名会话 ~60s 内 30~60 个连续请求即触发挑战（HTTP 200 + 挑战 HTML，非 429）；触发后评分衰减极慢（10 分钟零自愈），但**重过首页挑战可立即洗白**；≤0.15 req/s 慢速稳态可长跑。Guard 的核心从"限速计数"变为"评分预算管理 + 洗白调度"。
- **token 来源**：匿名 cookie（访问首页获取，易得、配额低）+ 可选小号登录 token（耐久）。`.env: XUEQIU_TOKENS` 逗号分隔，运行时可热加载补充。
- **健康度**：连续失败 ≥5 移出池，定时探测回归；单 token QPS 与全局 QPS 双重上限。
- **退避**：429/风控码指数退避（1s/2s/4s/…封顶 10min）+ 换 token 重试。
- **熔断**：池空 → 暂停整个调度器 + risk_alerts 告警（kind='xueqiu_circuit'），定时探测恢复。

### 4.5 数据模型（DDL 草案，实施时进 `app/db/schema.py` 幂等迁移）

### 4.6 写缓冲

轮询回的新增先进内存缓冲，**满 200 条或 60s** flush 一次批量 UPSERT——避免 5400 次轮询产生 5400 个小事务；进程退出前强制 flush；崩溃丢失上限 = 缓冲窗口内增量（可接受，兜底轮会重扫当日窗口补齐）。

### 4.7 监控

状态页新增卡片（复用 tushare_quota 卡片模式）：实时 QPS / 各档位覆盖进度 / token 健康 / 今日新增帖数 / 熔断状态；进度经 WS 推送（type='xueqiu_status'）。

## 9. P0 标定实测结果（2026-09-21）

> 环境：WSL2 本机、单 IP、匿名 token、curl_cffi（Chrome TLS 指纹）+ playwright headless（chromium-1234，executable_path 直指定，绕过 playwright 1.55 不支持 ubuntu26.04 的安装限制）。原始数据：`/tmp/xq_p0/`（ramp_result.json / wash_soak_result.json / token*.json）。

### 9.1 端点与数据面（全部确认）

- **个股讨论列表**：`GET https://api.xueqiu.com/query/v1/symbol/search/status.json?symbol=SH600519&count=20&page=1&sort=time&source=all&q=`
- **必须走 `api.xueqiu.com` 子域**：雪球网页 JS 的 host 路由表（从 main bundle 逆向确认）规定 `*.json` 请求默认路由到 api 子域；直接打主域 `/query/v1/...` 会被 WAF 按路径差异化拦截（弹挑战 HTML）。
- 旧端点 `/statuses/stock/list.json` 已下线（404）；`/query/v5/symbol/quote/status/list.json` 路径不存在（404）。
- `md5__1038` 动态签名参数**非必需**（不带可用）。
- **分页**：`page=1..maxPage`；count 上限 20（传 50 也只回 20）；**maxPage 多股抽样统一为 50**（count=20 时）→ 每股回溯窗口恒为 1000 帖。
- `sort=time` 严格时间倒序 → 游标增量（对比 last_status_id）成立。
- **字段全集**（list[] 每项）：`id / user_id / created_at(ms 时间戳) / text / description(富文本) / title / mark / view_count / like_count / reply_count / retweet_count / fav_count / source(Android/iPhone/HarmonyOS/雪球) / target / user / timeBefore / type / retweeted_status` 等——§4.5 表映射全部落实，另补充 `fav_count / type / retweeted_status`。
- 延迟：p50 140ms / max 400ms——数据面本身很健康，吞吐限制纯粹来自频控。

### 9.2 token 获取链路（重大修正）

- 雪球主域挂**阿里云 WAF JS 挑战**（`aliyun_waf_aa/oo/00` + 动态混淆脚本）：curl 与 curl-cffi（Chrome TLS 指纹模拟）均无法通过，**只拿得到 `acw_tc`，拿不到 `xq_a_token`**——必须真实浏览器执行 JS。
- **playwright headless 可稳定通过**（本机 chromium-1234 缓存 + executable_path），过挑战后一次拿全套 cookie（`xq_a_token` 40 字符 / `xq_r_token` / `xqat` / `xq_id_token` / `u` / `acw_tc`）。
- 匿名 `xq_a_token` 按 **IP 维度签发**：同 IP 重访首页拿到的是同一个 token（"多开浏览器造 token 池"不可行）。
- API 层（api 子域）平时不弹挑战、返回干净 JSON——**生产采集链路 = 纯 HTTP（curl_cffi + cookie），浏览器只用于 token 刷新/洗白**，两者彻底解耦。
- headless 直开个股页（/S/SH600519）会弹阿里云滑块验证（拟人拖动未通过）——**不需要进个股页**，纯 API 链路完全绕开。

### 9.3 频控真实形态（重大修正：行为评分制，非次数配额）

| 实验 | 参数 | 结果 |
|---|---|---|
| 加压 0.5 req/s | 60s | 27 成功后第 28 个触发挑战 |
| 加压 1 req/s | 到触发 | 58 成功后第 59 个触发（67s） |
| 触发后恢复观察 | 30s 间隔 × 20 次 | **10 分钟零自愈**（评分衰减极慢） |
| 浏览器洗白 | 触发后立刻 playwright 重过首页 | **即时恢复**（刷新仅 2s，xq_a_token 不变，WAF 会话 cookie 重置） |
| 慢速稳态 | 0.15 req/s × 15 min | **132 连发零触发** |

- 触发的表现是 **HTTP 200 + 挑战 HTML**（不是 429/400016）——采集器必须按"响应体是否 JSON"判定成败，不能只看状态码。
- 触发阈值 ≈ "60 秒时间窗 × 速率"的行为评分累计：0.5 req/s 约 28 个、1 req/s 约 58 个都在 ~60s 尺度触发；**>0.15 req/s 的持续稳态在匿名 token 下不可行**。
- 评分绑定 **WAF 会话 cookie（acw_tc 族）而非 xq token**：洗白不换 token，重过一次首页挑战即清零。
- 评分跨请求累积：上轮触发后间隔 ~5 分钟再打，第 1 个请求即触发（未衰减完）。

### 9.4 匿名 token 的可行生产形态（P1 前需拍板）

| 形态 | 机制 | 均摊吞吐 | 覆盖能力 | 风险 |
|---|---|---|---|---|
| **A 脉冲+洗白** | 每 ~25 请求主动 playwright 过一次首页（2~20s）清零评分 | ~0.5-0.8 req/s（4-7 万 req/天） | 全市场日内轮询（1.1 万/天）绰绰有余 | 每天数百次过 WAF 的长期存活未知，可能升级风控 |
| **B 慢速稳态** | ≤0.15 req/s 长跑不触发 | ~1.3 万 req/天 | 全市场每天一轮（**无日内时间序列**，情绪特征价值大减） | 最温和，被画像风险最低 |
| **C 登录 token 主力** | 小号登录的 xq_a_token | 未实测（社区经验配额高 1-2 个量级） | 预期可支撑原设计 1.2 req/s 稳态 | 需用户提供小号；封号风险由账号承担 |

推荐：**P1 试点以形态 A（脉冲+洗白）跑匿名链路验证机制，同时引入 1 个登录小号做形态 C 实测**；若 C 配额确如预期，生产主力切 C、匿名降级 fallback。

### 9.8 形态 C 实测定论（2026-09-21 晚，登录 token 已交接）

- 人工抽查 24 条发现「反驳/质疑型」集中误判：作者在**反驳唱空观点**，模型 reason 写对了（"反驳悲观情绪，认为市场由情绪主导"）却发出 -1 标签——**理解正确、映射相反**。

### 9.11 日常排期与详情页展示（2026-09-24）

**DAG 节点 `xueqiu_sentiment` + 独立流程（02:00）**

- 与 `margin_daily` 同一模式：帖子 24h 产生、由常驻 poller 断点采集，17:00 主流程跑时当日帖远未收全（盘后讨论才是散户情绪高发段），故独立流程凌晨跑完整日。
- **不做日期窗口**：不 score「某一天」，而是「所有未打分热帖」——既不依赖 poller 某时刻是否已抓全，也无需维护游标；`ON CONFLICT DO NOTHING` + 只取未打分 → 前夜漏网的次夜自动补，天然断点续跑。
- 打分主循环抽为 `run_scoring`/`score_pending`，CLI 与 DAG 节点共用一份实现；并发只在 LLM 调用，DB 写入固定主线程（commit 顺序 + psycopg2 单线程）；进度经 `progress_cb` 每 10 批（~30s）上报 `update_node_progress`，远低于看门狗 5 分钟阈值。
- 参数 `strategy_config.xueqiu_sentiment = {min_heat:5, max_posts:8000, workers:8}`。
- **排序口径修订**：原纯 `heat` 倒序在历史积压时（首次上线积压 1.3 万帖）会让近期帖排在老高帖之后——展示层要新帖、IC 体检要逐日截面完整，两者都被拖坏。改「发帖日倒序 → 日内热度倒序」，先填满最近一天再往前。实测日稳态 heat≥5 约 5,000 帖 / 1,070 股，8000 预算既跟得上新增又能约 3 夜填平积压。

**运维教训（两条，都是静默失败）**

1. **新建已发布流程会立即触发**：`cron_scheduler` 的到期判定是「距上一 cron 槽位 24h 内即触发 + `last_run_at` 幂等」。新建流程 `last_run_at IS NULL`，而其 cron 槽位（02:00）已在当日过去 → 创建后**立刻跑一次**。本次即为 17:58:25 触发。属设计内行为（重启补跑），但新增流程时要有预期。
2. **新增 DAG 节点的静默 no-op（更危险）**：`_execute_flow_internal` 对 `NODE_FN_MAP` 取不到的节点名**兜底为空操作 lambda**。后端进程持有的是启动时的模块快照，本次后端 09-23 启动、节点函数 09-24 才加入 → 流程"执行完成"仅用 **9 毫秒**、节点日志停在 `pending`，而任务状态是 success。已加 `logger.warning` 显式喊出，避免这类静默 success（同 margin_daily "静默 success 0 行" 一类）。**推论：改 DAG 节点代码后必须重启后端，否则改动不生效且不报错。**

**`pg_dump` 与 init_db 的锁冲突**

- 夜间 `backup_qiniu` 节点跑 `pg_dump -Fd -j 4`，其 4 个 worker 在整个 dump 期间持有**全库 ACCESS SHARE 锁**（表现为长时间 `idle in transaction`）→ 期间任何 `ALTER TABLE`（需 ACCESS EXCLUSIVE）都会排到 dump 之后；而一个**在等锁的 ALTER 会阻塞该表后续所有读**。
- 本次 `init_db` 撞上该窗口：雪球三个视图因锁超时跳过（无害，定义未变），但 `ALTER TABLE factor_ic_stats` 排队等锁 → 遂 kill 掉该进程、只单独执行本节点的种子 INSERT。**结论：init_db / 迁移不要在夜间流程或备份运行期间跑。**
