## 1. Git Commit 纪律

### 1.1 强制提交节奏

每进行 **20 轮对话**（Reasonix 会话对话轮次），无论功能是否完成，必须执行一次：

```bash
git add -A
git commit -m "<type>: <简短描述>"
```

例外：如果中途完成了可独立交付的特性，可以提前 commit，但最多不超过 20 轮。

### 1.2 Commit Message 格式

```
<type>: <简短描述>

type: feat / fix / refactor / docs / chore / style / perf
```

示例：
```
feat: 新增 PE 分位图接口
fix: _fetch_ohlcv exchange 列名歧义导致特征计算失败
refactor: 移除废弃的 stock_indicators_* 6 张表
```

### 1.3 Commit 内容要求

- 在 commit message 末尾附上本轮涵盖的关键功能点或优化点（1-3 行）
- 如果一个 commit 涉及多个独立改动，考虑拆分

## 2. 新功能 → 设计文档同步

### 2.1 同步时机

新功能上线后、对应的 Git commit 之前。

### 2.2 同步范围

| 变更类型 | 需同步的文档 |
|----------|-------------|
| 新增 API 端点 | `design/03-API接口文档.md` |
| 新增模块/重构模块 | `design/01-系统架构.md`（目录结构、已知实况）+ `design/02-模块功能与数据流程.md`（模块职责、数据流） |
| 新增前端页面/组件 | `design/04-前端架构与页面.md`（组件清单 + 路由表 + Store 清单） |
| 新增数据库表 | `design/01-系统架构.md`（更新 §6 表总览） |
| 新增 DAG 节点 | `design/02-模块功能与数据流程.md`（更新 §3.2 NODE_FN_MAP） |
| Bug 修复 | `design/开发规则.md`（更新 §3 Bug 修复历史） |
| 开发规范 | `design/开发规则.md`（更新 §4 可复用模式、§5 部署纪律） |

### 2.3 版本号更新

每次 01-系统架构.md 有结构性变更时更新版本号：
- 大版本（架构重构、模块新增）：`vX.(Y+1)`
- 小版本（API 扩展、Bug 修复）：`vX.Y` + 更新最后更新日期

## 4. 可复用开发模式

### 4.1 前端 WS 监听模式

WS 消息监听必须在触发操作（如 POST 请求）**之前**注册，避免竞态丢失早期消息。

```javascript
// ✅ 正确：先注册监听，再发请求
listenProgress(null, featureId)  // taskId=null 表示宽匹配
const r = await axios.post('/api/...')
listenProgress(r.data.task_id, featureId)  // 拿到真实 ID 后精确匹配
```

### 4.2 后端后台线程状态管理

后台线程必须覆盖所有退出路径的状态设置：

```python
# ✅ 正确：每条路径都设 status
if error_condition:
    task["status"] = "failed"
    task["error"] = "..."
    return
# 正常完成
task["status"] = "completed"
```

### 4.3 SQL JOIN 时列名前缀

任何 JOIN 查询中的列名必须加表前缀，避免 AmbiguousColumn：

```sql
-- ✅ 正确
SELECT a.stock_code, a.trade_date FROM daily_quote a
JOIN stock_master b ON a.stock_code = b.stock_code
WHERE a.exchange IN ('SSE','SZSE')

-- ❌ 错误
SELECT stock_code, trade_date FROM daily_quote
JOIN stock_master ON daily_quote.stock_code = stock_master.stock_code
WHERE exchange IN ('SSE','SZSE')
```

### 4.4 DB Schema 废弃表清理流程

废弃一张数据库表的完整步骤：
1. `app/db/schema.py` — 删除 DDL + TABLES 注册
2. `app/api/*.py` — 删除相关的 API 端点
3. `crawler/*.py` / `scripts/*.py` — 删除/修复引用代码
4. `web-v2/src/components/*.vue` — 删除相关前端组件
5. `AGENTS.md` + `design/`（01/02/04 按变更类型）— 更新文档
6. 生产环境手动 DROP TABLE（确认无数据需要后）

### 4.5 前端组件清理确认

删除前端组件前，先全局搜索确认无 import 引用：
```bash
grep -rn "ComponentName" web-v2/src/
```
零结果才可删除。保留 `.bak` 备份至少一个版本周期。

### 4.6 后端 import 编译验证

编辑后端文件后，先验证编译再依赖热重载：

```bash
source venv/bin/activate && python3 -c "from app.module import symbol"
```

如果编译失败，热重载不会重启进程（旧进程继续运行），不会连带杀掉前端。

## 5. 设计文档维护

### 5.1 文档位置

| 文档 | 位置 | 职责 |
|------|------|------|
| 架构设计 | `design/01-系统架构.md` | 技术栈、目录、启动流程、表总览、已知代码实况 |

| API 参考 | `design/03-API接口文档.md` | 所有 REST API 请求/响应 |
| 前端架构 | `design/04-前端架构与页面.md` | 路由、store、页面组件、WS、主题 |
| 专项设计 | `design/05-Qlib移植设计.md` 等 | 专项设计文档（含实施结果） |
| 开发规则 | `design/开发规则.md` | 本文件 |
| Bug 历史 | `design/开发规则.md` §3 | 本文件 |

### 5.2 文档格式

- 中文正文，代码标识符保留英文
- 版本号 `v<主>.<副>` + 最后更新日期
- Markdown 表格 + 代码块

### 6.1 改代码前必须先反问

每次动手改代码前，必须先反问至少一个问题。例如：
- 确认需求的具体边界（"这个功能是给谁用的？什么场景触发的？"）
- 对比至少两种实现方案（"方案 A 和方案 B 各有什么代价？"）
- 确认不影响已有功能（"改了 X 之后，Y 会受影响吗？"）

禁止：不经过确认直接进入编码。这条规则适用于所有修改（包括 Bug 修复）。
